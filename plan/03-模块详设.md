**纪律**
- 只认 `diff --git a/<p> b/<p>`、`@@ -a,b +c,d @@`、`+`/`-`/` ` 行；`\ No newline at end of file` 忽略。

## 1. `fidelity` — Merge 保真度扫描

### 1.1 命令

```
mergefidelity fidelity scan <repo> [--range=REV|A..B] [--all]
                                [--since=REV] [--until=REV]
                                [--show-kind=smuggled,dropped,resolution,all]
                                [--show-resolution] [--fail-on=smuggled|dropped|any]
                                [--format=json|md] [--out=PATH] [--as-of=YYYY-MM-DD]
```

> 命令形态与题面 §二「招牌动词表」一致：`fidelity` 是命令族，`scan` 是其动作。

### 1.2 处理顺序（固定）

1. 环境检查（git ≥2.38、是仓库）。
2. 枚举：`rev-list --merges --reverse --topo-order <range>`。
3. 批量 payload：`git log --merges --remerge-diff -p --no-renames --format=%H%x00%P`，一次进程。
4. 对每个 merge：
   - 父提交数 >2 → `SKIPPED(octopus)`，**不进分母**。
   - 命中自定义 merge driver 的路径 → `SKIPPED(custom_driver)`，**不进分母**。
   - `recorded_tree = <merge>^{tree}`；`mechanical_tree = merge-tree(...)`（隔离对象目录）。
   - `blob_fidelity` 按 §4.2；path 只在单侧时进 `path_only_in_recorded/mechanical`。
   - hunk 分类：以 `git diff -U0 <mechanical_tree> <recorded_tree>` 为**唯一方向**，按 hunk 自身形态
     三分（含冲突标记 → `RESOLUTION`；含 `+` 行 → `SMUGGLED`；只含 `-` 行 → `DROPPED` 候选）。
     **判定以本式为准**（golden 也是这么算的）；remerge payload 用于**交叉校验与降噪**：
     若 payload 里出现的路径不在树 diff 的路径集合里，记 `CROSSCHECK_MISMATCH`（进报告
     `warnings`，不进 golden、不改判定），而不是静默取其一。
   - `DROPPED` 需二次扫描 `--find-object=<blob> --all` 判断"后续是否重引入"；找不到重引入才算 DROPPED。
5. 排序 + 汇总 + 渲染。

### 1.4 测试点

- 10 个 fixture 的 golden 逐字节（`expect.json` 已是规范 JSON + `digest`）。
- 连跑两次逐字节一致。

- 自定义 driver fixture：`reason == "custom_driver"`。

## 2. `parity` — 跨分支补丁对齐

### 2.1 命令

```
mergefidelity parity <repo> --from=A --to=B [--format=json|md]
                                   [--out=PATH] [--no-apply-fallback]
```

### 2.2 处理顺序

1. 候选集：`rev-list --cherry-pick --right-only A...B`；`git cherry -v A B` 交叉核对（数量不一致 → `warnings` 字段，不失败）。
2. 顺序：**按 `rev-list` 的输出顺序逐条处理**（M3 实测定案：这才是 golden 的顺序，也省掉一层额外口径；
   本条原写"按 `(commit_time, oid)` 排序"是笔误，已更正。见 `plan/00` 决策记录表与 `plan/HANDOFF-M4.md`）。
3. 对每个 commit：`diff-tree -p -U0 <c>^ <c> | patch-id --stable`。
4. 建立 A 侧 `patchid → [commit]` 索引（含路径集合）；`equivalent_source` 取索引首项
   （`git rev-list --reverse A` 的"最早到达者"，可复现）。
5. 判定优先级（§4.4）：
   - `PRESENT`：`-U0` patch-id 相同（路径参与 patch-id，路径不同即不同）。
   - 否则若允许 apply 兜底：临时 worktree **detach A（源侧）**（问的是"这个改动在 A 里了吗"；
     挂 B 侧会因候选本就来自 B 而恒成功），apply 用 **-U3** 上下文：
     `apply --reverse --check` 成功 → `PRESENT(basis=apply)`；`apply --check` 成功 → `MISSING`；两者皆失败 → `MODIFIED`。
   - 同内容落在另一个路径 → 不判 `PRESENT`，只在 `note` 写 `content_equivalent_at_other_path`（只提示不改判定）。
   - `--no-apply-fallback`：只给 patch-id 口径的结论——命中即 `PRESENT(basis=patchid)`，
     未命中一律 `MODIFIED(basis=patchid)`（**没有 apply 证据就不声称"缺失"**）。
6. `patch_parity = present / total`；分母 0 → `null`。

### 2.3 JSON 结构

```json
{
  "from": "release/1.0", "to": "main",
  "from_oid": "…", "to_oid": "…",
  "candidates": 5,
  "present": 3, "missing": 1, "modified": 1,
  "patch_parity": 0.6,
  "commits": [
    {"commit":"…","subject":"…","u0_patchid":"…","status":"PRESENT",
     "basis":"patchid","equivalent_source":"…","paths":["src/x.py"]}
  ],
  "digest": "…"
}
```

### 2.4 测试点

- 双向 release/main fixture：同一修复换上下文（第 2 行 vs 第 5 行）→ `PRESENT`。
- 纯空白差异（4 种形态）→ 同 patch-id → `PRESENT`。
- 部分应用 → `MODIFIED`。
- 真缺失 → `MISSING`。
- worktree 清理：成功路径与人为异常路径后 `git worktree list` 只剩主工作树。
- `--no-apply-fallback` 下不创建任何 worktree。

## 3. `ledger` — Revert / 复活账本

### 3.1 命令

```
mergefidelity ledger <repo> [--range=REV|A..B] [--format=json|md] [--out=PATH]
```

### 3.2 处理顺序

1. 枚举：`log --grep='^This reverts commit' --format=%H\x1f%B\x1e <range>`——`\x1e` 切提交记录、
   `\x1f` 切 OID 与正文（**不要用 `%H%x00%B` 再按 `\x00\x00` 切**：单条能过，多条会粘成一条）。
2. 从正文正则提取被回滚 OID：`^This reverts commit ([0-9a-f]{7,64})`（`re.MULTILINE`），再
   `rev-parse --verify <oid>^{commit}`；解不出来（对象库没有该提交）→ **跳过该条**（不猜）。
3. 校验：revert commit 的 `U0_patchid` vs **被回滚 commit 的 diff 取反**（`diff-tree <c> <c>^`，`a/`/`b/` 由 git 自行互换后算 patch-id）。不等 → `REVERT_UNVERIFIED`。
4. 重放：`log --find-object=<blob> --all`（被回滚 commit 触及的 blob）**收窄候选**，再对候选提交算 `U0_patchid`，与原始一致 → `REVERTED_THEN_REDONE`。**筛选集落空时必须回到全量 later 提交复扫**，复扫仍无才 → `REVERTED_NO_SUCCESSOR`——`--find-object` 认 blob 内容、`U0_patchid` 对空白免疫，"只差空白 + 文件别处已变"的重新落地会**同时**躲开筛选与直觉，只做筛选就会静默漏报（K44）。**结论口径以 patch-id 相等为准**，`--find-object` 只是加速命中的筛选。
5. 去重：同一 revert 只入账一次；排序 `(被回滚 commit_time, revert oid)`。

### 3.3 JSON 结构

```json
{
  "entries": [
    {"revert_oid":"…","reverted_oid":"…","reverted_subject":"…",
     "reverted_commit_time":1767225720,
     "status":"REVERTED_THEN_REDONE","verified":true,
     "successor_oid":"…","paths":["src/x.py"]}
  ],
  "counts": {"no_successor":1,"then_redone":1,"unverified":1},
  "unavailable": [],
  "digest": "…"
}
```

> 条目字段与 `expect.json` golden **逐项一致**：初稿里的 `evidence`（`patchid|find-object`）
> 已去掉——"用什么方式判的"是**实现细节**，`verified`（反向 patch-id 校验通过与否）加
> `successor_oid` 已承载全部结论信息，多一个字段会让"逐项一致"变成"逐字段猜"（同 M2 的
> `octopus` 只输出 `reason`）。`--find-object` 不可用时的 `reason` 落在 `unavailable`，不在条目里。

`--find-object` 不支持时：`unavailable: [{"reason":"git_too_old","capability":"find-object"}]`，状态只给 `REVERT_UNVERIFIED`，**不猜**。

### 3.4 测试点

- 三状态各一 fixture。
- `patchid_mismatch` fixture：revert 正文声称回滚 X，实际 diff 回滚 Y → `REVERT_UNVERIFIED`。
- 同一 revert 重复出现在多个 range 查询中只入账一次。
- `UNAVAILABLE` 与"无 successor"是不同输出。

## 4. `report` — 确定性报告 + 可复现摘要

### 4.1 命令

```
mergefidelity report <repo> [--range=…] [--format=json|md]
                            [--out=PATH] [--verify=PATH] [--as-of=YYYY-MM-DD]
                            [--parity-from=REF --parity-to=REF]
```

- 输入 = 前三个模块的原始结果，**在同一对象库上现跑一次**（不读缓存文件）。`fidelity` 与 `ledger` 恒计入；`parity` 需要两个显式引用，未给时该节为 `null` 并在 `notes` 写明 `parity_not_requested`（**不伪造空结果**）。两个引用必须**成对**给出（只给一个 → 用法错误 2）。
- `--verify=PATH` → 读回报告，用同一对象库重新推导，逐字节比较；不等 → 退出码 1，输出首个差异 `{"json_path", "expected", "actual"}`。

### 4.2 报告头（写死，参与 digest）

`tool_version`、`git_version`、`object_format`、`gitattributes_oid`、`config_overrides`、`range`、`as_of`、`findings_digest_algorithm: "sha256"`。

**禁止**：扫描时刻、绝对路径、主机名、用户名、locale、Python 版本。

`gitattributes_oid` 取**范围右端**（`fidelity.range_end`：`A..B`→`B`、单 REV→它自己、无范围→`HEAD`），与 `fidelity` 的 `end_rev`、`ledger` 同口径（K45）。

`as_of` 未显式给出时取**三源 `as_of` 的最大值**（不另算一份时间戳）：`fidelity` / `ledger` / `parity`
各自都已把"本模块输入里的最新提交时间"算成日期，且空输入都回落 `end_rev`（默认 `HEAD`）——
直接取最大值最省口径，也不会漏掉 parity（它只给日期不给时间戳）。空仓库无提交时才回落 `end_rev`。
**M5 实测抓出的回归**：初版用 `max([] or [0])` → 空输入落成 `1970-01-01`，与同一仓库的
`fidelity`/`ledger` 给出不同 `as_of`。复现 `test_report.py::test_as_of_falls_back_to_head_on_empty_input`；
变异验证：把回落去掉 → 该测试变红。

### 4.3 `--verify` 算法

1. 读文件 → `json.loads`（坏 JSON → 退出码 2；缺 `digest` 字段 → 退出码 2，**缺字段 = 坏报告**）。
2. 用 `verify_range` 重新跑模块（同一 `as_of` / range / parity 引用），生成规范 JSON。
3. 与读回报告**去掉 `digest` 字段后**逐字节比较；首个差异用 JSON path 表达（`fidelity.merges[3].hunks[1].new_range`）。
4. 内容一致但 `digest` 自校验不过（只改了 `digest` 自身）→ 退出码 1，定位到 `digest`。
5. 两者都过 → 退出码 0，stdout 打 `verified: N merges, M findings`。

> **定位顺序是"先内容、后 digest"**（M5 定案）：若先查 digest，任何内容篡改都会先命中 `digest`
> 字段，把"哪一处被改了"这个真正有用的答案盖掉。digest 负责**发现**不一致，JSON path 负责
> **定位**，定位必须落在真实差异上。变异验证：把 digest 检查挪到前面 → 两条篡改测试变红。

### 4.4 `findings` 的构成（M5 定案）

`findings` 把三个模块的结论统一成**内容寻址 finding**（§4.5 的 ID 口径），排序键
`(commit_time, commit_oid, path, old_range)`：

| 来源 | `kind` | `old_range` / `new_range` | 展开方式 |
|---|---|---|---|
| `fidelity` | `SMUGGLED` / `DROPPED` / `RESOLUTION` | hunk 的旧/新区间 | 每个 hunk 一行（`fidelity.findings_of`） |
| `ledger` | `REVERTED_NO_SUCCESSOR` / `REVERTED_THEN_REDONE` / `REVERT_UNVERIFIED` | `-`（revert 账目没有 diff 区间） | 每条 revert 的每个路径一行（`ledger.findings_of`） |
| `parity` | `PARITY_MISSING` / `PARITY_MODIFIED` | `-`（候选提交没有单一区间） | 每个候选的每个路径一行（`parity.findings_of`）；`PRESENT` 不是事故，不入账 |

- 展开逻辑住在**各自模块**里（它们才是 ID 口径的产出方），`report.collect_findings` 只汇总与排序。
- finding 记录字段固定 7 项：`id` / `kind` / `commit_oid` / `commit_time` / `path` / `old_range` / `new_range`。
- `commit_time` **不参与 ID**，只参与排序；`commit_oid` 是"挂在哪个提交上"（fidelity 的 merge /
  ledger 的 revert / parity 的候选提交），字段名刻意不叫 `merge_oid`（三类来源都在用）。

### 4.5 测试点

- 同 fixture 两次生成逐字节一致；`TZ=America/New_York` 与 `TZ=Asia/Shanghai` 下 digest 相同。
- `core.quotepath=true/false` 下 digest 相同（因路径已用 `-z` 强制原样读出）。
- 篡改一个字节 → 退出码 1 且 `json_path` 指向被改字段（含嵌套 `fidelity.merges[0].hunks[0].new_range`）。
- 只改 `digest` 自身 → 退出码 1 且定位到 `digest`；手工删掉 `digest` 字段 → 退出码 2。
- `parity` 未请求时 `null` + `notes`；请求时 `PARITY_*` finding 入账。
- 报告头**禁止字段**断言：无绝对路径、无 `python_version` / `scan_time` / `hostname` / `locale`。
- `docs/report-sample.json`（入仓样例）能被当前构建 `--verify` 通过。

## 5. `gate` — CI 门禁 + 过期基线

### 5.1 命令

```
mergefidelity gate <repo> --baseline=PATH [--since=REV] [--fail-on=smuggled|dropped|any]
                          [--as-of=YYYY-MM-DD] [--format=json|md] [--out=PATH]
```

### 5.2 处理顺序

1. 解析基线（受限 TOML）。语法错误 / 缺 `justification` / 坏日期 / 空基线 → 退出码 2，**零副作用**（基线先解析，此时还没跑扫描、没写任何产物）。
2. 跑 fidelity（`--since` 增量；未给则全量）。**全量收集 `SMUGGLED` + `DROPPED`**（见 §5.5）。
3. 分类：
   - finding 命中基线且 `as_of <= expires` → `baselined`（不计失败）。
   - 命中且 `as_of > expires` → `expired`（参与失败）。
   - 未命中基线 → `new`（参与失败，按 `--fail-on` 过滤 kind）。
   - 基线条目无对应 finding → `stale`（只提示）。
4. 退出码：`new` 或 `expired` 非空 → 1；否则 0；用法/基线坏 → 2；环境 → 3。

### 5.3 基线格式（与 `data/README.md` §4.7 一致）

```toml
[[finding]]
id = "0123…"
expires = "2026-12-31"
justification = "已知的机械合并上下文差异，见 #12"
```

**受限 TOML 子集**（3.8 无 `tomllib`）：只支持 `[[finding]]` + 字符串值 + 注释；遇到数组/嵌套表/多行字符串/非字符串值 → `toml_unsupported`（退出码 2，**明示行号**）。`id` 精确匹配，不做前缀/模糊匹配；同一 `id` 重复登记 → 语法错误。

### 5.4 测试点

- 新增 1 个夹带 → 1 且只报新增。
- 旧账未过期 → 0，`baselined == 1`。
- `expires` 改到过去 → 1，`expired == 1`。
- 基线语法错误 → 2，输出行号，且不写任何产物。
- 基线指向不存在 finding → `stale == 1`，退出码仍 0。
- 同一输入两次运行退出码一致。
- `as_of <= expires` 边界当天算未过期（`as_of == expires` → `baselined`）。

### 5.5 `--fail-on` 只过滤 `new`（M5 定案）

门禁扫描**全量收集 `SMUGGLED` + `DROPPED`**，`--fail-on` 只决定 **`new`**（未命中基线的新增）是否参与失败。

理由：`baselined` / `expired` 是对"基线条目是否仍然命中"的回答，必须覆盖全部事故类；若为了省事
只扫 `--fail-on` 那一类，另一类的基线条目会因"没扫到"而变成 `stale`——**一条已登记在案的旧账被
误报成"已修复"**。实测复现：`test_gate.py::test_baseline_coverage_is_not_filtered_by_fail_on`；
变异验证：把 `_scan_kinds()` 改成返回 `FAIL_ON_KINDS[fail_on]` → 该测试变红。

### 5.6 退出码与报告字段

`baseline_entries` / `fail_on` / `counts`（`baselined`/`expired`/`new`/`stale`）/ 四个 bucket 列表
（每项含 `finding` / `expires` / `justification`，`stale` 项没有 `finding`）/ `scan`（fidelity 的 `summary`）。

## 6. CLI 契约

```python
def build_parser() -> argparse.ArgumentParser   # 唯一事实源
def main(argv=None) -> int                      # 返回码，不调 sys.exit（__main__ 里 sys.exit(main())）
```

- 未知子命令/缺参数：argparse 原生 `SystemExit(2)`；`main()` 捕获后统一返回 2（测试两条路径都覆盖）。
- `--version` → `mergefidelity 0.1.0`。
- `-h` 全中文说明；错误信息中文 + 英文关键词（便于 grep）。
- 每个子命令都支持 `--out`；不写 `--out` 时输出 stdout。
- **入口编码守卫**：`_ensure_utf8_stdio()` 按 `stream.encoding` 探针决定是否 `reconfigure(encoding="utf-8")`，cp936 控制台保持不动。
