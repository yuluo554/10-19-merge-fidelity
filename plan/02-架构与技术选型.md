# 02 · 架构与技术选型

> 上游：`plan/01-题目文档.md`（需求）与 `data/README.md` §四（数值口径，唯一权威）。
> 本文只回答"怎么搭"，不重复定义口径；两者冲突时以 `data/README.md` §四 为准。

## 一、形态与约束

| 项 | 定案 | 理由 |
|---|---|---|
| 交付形态 | 纯本地 Python CLI（单一形态） | 题面 §六；无 GUI/Web/服务端 |
| Python | `>=3.8`（本机有 3.8.8 / 3.12.10） | 用户拍板；CI 跑 `{windows,ubuntu} × {3.8,3.12}` |
| 运行时依赖 | **零第三方依赖**（仅标准库） | 可审计、可在任意机器 `pip install -e .` |
| 开发依赖 | `pytest`（`.[dev]`） | 测试面 = 安装面，README 与 CI 用同一 extras |
| git | ≥2.36（`--remerge-diff`）/ ≥2.38（`merge-tree --write-tree`） | 低于门槛退出码 3，不降级猜测 |
| 网络 | 零网络调用 | 隐私红线；报告不写绝对路径/主机名/用户名 |
| 写入面 | 只读仓库对象；**不写 `.git/objects`** | 见 §三 的对象隔离 |
| 许可证 | MIT | 用户拍板；仓库内含 `LICENSE` |
| 发布附件 | 手工源码包（`git archive` + `SHA256SUMS`） | 字节可复算、与 tag 树逐源 |

## 二、分层架构

```
                 ┌──────────────────────────────┐
  CLI (argparse) │ mergefidelity.cli            │  参数 → 退出码（0/1/2/3）
                 └───────┬──────────────────────┘
                         │ 只调用编排层，不做判定
     ┌───────────────────┼────────────────────┬──────────────────┐
     ▼                   ▼                    ▼                  ▼
 fidelity.py          parity.py           ledger.py          gate.py
（merge 保真度）    （跨分支对齐）       （revert 账本）    （基线门禁）
     └───────────────────┴─────────┬──────────┴──────────────────┘
                                   ▼
                          report.py（规范 JSON + digest + --verify）
                                   ▼
        canonical.py（键序/排序/序列化/digest/finding id）   ← 唯一写盘出口
                                   ▼
        gitobj.py（子进程封装、版本门槛、只读对象访问、临时对象目录）
                                   ▼
                              git 可执行文件
```

**分层纪律**

1. **CLI 只做参数解析与退出码映射**；任何判定都在模块里。新增子命令时 `build_parser()` 是 README/测试反射的唯一事实源。
2. **写盘只有一个出口**：`canonical.write_atomic()`（临时文件 + `os.replace`），参数冻结为 `ensure_ascii=False / sort_keys=True / separators=(",", ":") / 结尾 \n / UTF-8 无 BOM`。
3. **判定不读时钟**。报告里的 `as_of` 只能来自 `--as-of` 参数或提交时间；基线过期按 `as_of` 比较。
4. **异常只在两处被转成退出码**：CLI 入口（用法错误 2）与 `gitobj`（环境不满足 3）。模块层抛带码异常，不 `sys.exit`。

## 三、git 访问层设计（`gitobj.py`）—— 本项目最关键的一层

### 3.1 三个只读探针的实测结论（2026-10-18，git 2.54.0.windows.1）

| 探针 | 实测事实 | 架构后果 |
|---|---|---|
| `merge-tree --write-tree --merge-base=B P1 P2` | **会向对象库写 tree/blob**（若不加隔离，`.git/objects` 文件数增加） | 必须设 `GIT_OBJECT_DIRECTORY=<tmp>/objects` + `GIT_ALTERNATE_OBJECT_DIRECTORIES=<repo>/.git/objects`，用完删临时目录 |
| 同上，冲突场景 | exit 1；**stdout 首行仍是 tree OID**，随后是 `100644 <oid> 1\t<path>` 三元组；该 tree 内文件含 `<<<<<<<` 标记 | 冲突也走同一解析路径；树内容可读但必须标 `has_conflict` |
| `log --merges --remerge-diff`（octopus） | 只往 stderr 打 `Skipping remerge-diff for octopus merges.`，payload 为空 | **不靠 stderr 判 octopus**，用父提交数 >2 判，stderr 仅作为交叉核对 |
| `patch-id --stable` + `-U0` | 跨行号同 id、`b b` / `b    b` / `b<TAB>b` / 行尾空格同 id；**对路径敏感**（不同文件同内容 → 不同 id） | 等价判定必须带上路径语义：`PRESENT` 要求 patch-id 相同**且**路径可映射或由 apply-check 兜底 |
| 忠实 merge | remerge-diff payload 为空（`%H\0%P` 后无 diff） | "空 payload" = 忠实，不产出 finding |
| 冲突解决 | payload 含 `remerge CONFLICT ...` 行 + 冲突标记被删的 hunk | hunk 分类要先剥离 `remerge CONFLICT` 行再判 SMUGGLED/DROPPED |

> 以上每条都由 `tests/test_gitobj.py` 的 fixture 复算锁住（M2 起），不写成注释级"我以为"。

### 3.2 子进程纪律

- 一律 `subprocess.run([...], capture_output=True)` 且 **显式 `encoding="utf-8", errors="replace"`**（`text=True` 走 locale，CI 会 `UnicodeDecodeError`）。
- 固定 `-c core.quotePath=false -c core.pager=cat --no-pager`，报告头登记生效的 `-c` 项。
- 固定 `--no-renames`（口径 §4.1）；不设 `GIT_DIR`，用 `-C <repo>`。
- 所有命令带 60s 超时；超时归"环境不满足"（退出码 3）而不是业务失败。
- 版本门槛在**入口处一次**检查（`fidelity`/`report` 需 2.38；`ledger` 的 `--find-object` 需 2.16，不满足只降级 ledger）。

### 3.3 临时 worktree（仅 parity 兜底）

- 路径：`<repo>/.git/mergefidelity-worktrees/<pid>-<counter>-<rand6>`？**否** —— 题面要求"不建 worktree 之外的持久状态"，且 `.git` 只读。
  定案：`tempfile.mkdtemp(prefix="mf-parity-")`（系统临时目录）+ `git worktree add --detach <tmp> <B>`。
- `try/finally` 双路径清理（`worktree remove --force` → `worktree prune` → `rmtree`），并在测试里断言 `git worktree list` 无残留。
- 报告里只出现相对路径或 `<temporary-worktree>` 占位，不落绝对路径。

## 四、确定性架构

| 层 | 确定性手段 |
|---|---|
| 枚举 | `rev-list --merges --reverse --topo-order`；排序键 `(commit_time, oid)` |
| 批量读 | 单进程 `git log --merges --remerge-diff -p`（实测全量 ≈1.3s/357 merges；逐进程 `merge-tree` ≈94ms/次） |
| hunk 解析 | 自写 unified-diff 解析器（不引第三方），行号按 hunk 头 0 基记录 |
| finding 排序 | `(commit_time, oid, path, old_range)` |
| 序列化 | `sort_keys=True`、`separators=(",", ":")`、LF、尾部换行、无 BOM |
| digest | `sha256(canonical_json_without_digest_field)`，字段顺序固定 |
| 时间 | 报告只写 `as_of`（显式参数或 `--until` 的提交时间），**不写扫描时刻** |
| 路径 | 仓库内相对路径；报告不含 worktree/临时目录绝对路径 |
| 时区 | `TZ` 与 `core.quotepath` 不影响 digest（测试覆盖） |

## 五、退出码契约（全项目唯一表）

| 码 | 含义 | 触发点 |
|---|---|---|
| 0 | 成功且无"需失败"的发现 | 全部子命令 |
| 1 | 成功执行，但存在需失败的发现（gate 新增/过期；`fidelity --fail-on` 命中） | gate / fidelity |
| 2 | 用法错误：未知子命令、缺必填参数、坏基线语法、坏报告文件 | CLI / gate / report |
| 3 | 环境不满足：git 版本低于门槛、仓库不存在/不是 git 仓库、git 调用超时 | gitobj |

> `SKIPPED(reason=octopus|custom_driver)` **不参与退出码**（题面 §二 模块①）。
> `sys.exit(2)` 的 argparse 原生行为统一保留；测试用 `pytest.raises(SystemExit)` 断言 `.code == 2`。

## 六、技术选型与弃选

| 选型 | 结论 | 理由 |
|---|---|---|
| 自写 unified-diff 解析器 | 采用 | 需要 0 基行号与 hunk 级归并；`git diff` 输出格式固定，几十行即可，且避免依赖 |
| `tomllib` | 不用（3.11+） | 底线 3.8；自写受限 TOML 子集解析器，超集形态显式 `toml_unsupported` |
| 第三方 CLI 框架（click/typer） | 弃 | 零依赖红线；argparse 足够，且便于 README↔CLI 反射对账 |
| `dulwich` / `pygit2` | 弃 | 会引入第二套 git 语义；"git 自己就是裁判"要求直接调 git |
| 解析 `git log` 文本 instead of `merge-tree` | 弃（只作降噪主路径） | remerge-diff 拿不到 `mechanical_tree` OID；两者是**交叉校验**关系，不是替代 |
| 全量逐 merge 调 `merge-tree` | 弃 | 实测 Windows 进程开销 ≈94ms/次；只对 payload 非空的 merge 复算 |
| 多线程/并发 git 子进程 | 弃（首期） | 确定性优先；bench 只做串行基线 |

## 八、已知边界（写进 README，不美化）

- octopus merge、自定义 merge driver 命中路径 → `SKIPPED`，不做近似分析。
- 跨平台只在 Windows 实测；Linux/macOS 由 CI 矩阵覆盖，行为差异按 CI 结果如实补记。
- 大型仓库（>10 万提交）无样本，首期不承诺规模上限。
- `blob_fidelity` / finding 是"机械合并 vs 实际记录"的差异证据，**不等于"这段代码错了"**。
