# 10-19-merge-fidelity · Merge 保真度审计（题目文档）

> - **性质**：不参赛项目题（无赛事锚点；含金量锚点 = 需求侧原话 + git 对象层可复算 + 三类事故合一本账）
> - **目标产出**：仓库 `10-19-merge-fidelity`（MergeFidelity / Merge 保真度审计器），发布 GitHub **公开仓库**，署名 yuluo554
> - **版本史**：v1 2026-10-17（初稿定稿；查证基准日 2026-10-17，GitHub 检索实测窗口 2026-10-18 10:33–11:12 UTC）
> - **交付形态**：**纯本地 Python CLI（只读 .git，零网络、无模型）**。单一形态，不设备选：所有判断都由 `git` 自己的合并引擎与 patch-id 复算得出，不调用任何网络接口，不加载任何模型权重。
> - **定位宣言**："对每一次 merge，用 git 自己的合并引擎复算'机械合并应该得到什么'，再与仓库里实际记录的树逐 blob 对比，挖出评审看不见的三类代码事故：**夹带（evil merge）、静默吞掉（conflict 解决时丢掉一侧 hunk）、跨分支漏搬（hotfix 没 forward-port / 补丁没 backport）**。每条发现都有内容寻址的 ID 与可复现 digest——git 自己就是裁判。"

## 一、介绍

**痛点**：评审看的是 PR 的 diff，而 merge commit 的树是**人手工解冲突、手工补代码**之后的产物。评审通过 ≠ 合进去的树正确。事故有三类，且都不在常规 review 视野里：

1. **夹带（evil merge）**：解冲突时顺手塞进与冲突无关的改动，或者干脆"修一下看起来不对的地方"。这类改动没有出现在任何一侧的 diff 里，只存在于 merge 结果树中。
2. **静默吞掉（silent drop）**：解冲突时选错一侧、或手工删掉了一段本应保留的 hunk。测试可能仍然通过，缺陷潜伏到线上。
3. **跨分支漏搬（missing port）**：hotfix 只落在 release 分支、没回流到 main；补丁 backport 到一半；cherry-pick 漏选。分支越多，漏得越多。

**判定（⬜ 软论据）**：evil merge 有 1 个 8★ 竞品；静默丢代码有 1 个 0★ 单日项目；跨分支补丁对齐只有 2012/2013 的停更工具与"必须改历史"的 hook 方案。**三者合并成"可复算账本 + 内容寻址证据 + CI 门禁"是空的**——但这是检索推断，不是市场调查。

**与 8★ 竞品 fimskiy/Evil-merge-detector 的三点差异（如实记录，不宣称首创）**：

1. **Python 标准库零依赖、只读 `.git`**：竞品为 Go 二进制，须单独分发；本题 `pip install` 即用，且对仓库**不写任何对象、不建 worktree 之外的持久状态**（临时 worktree 用完即删）。
2. **三类事故合一本账**：竞品只做 evil merge；静默吞掉与跨分支漏搬需要同一份 commit 图与同一套 patch-id 口径才能对上号，分成三个工具就永远对不上。
3. **内容寻址 + 可复现 digest + 过期基线门禁**：每条 finding 的 ID 由 `sha1(merge_oid ‖ path ‖ old_range ‖ new_range ‖ kind)` 决定，报告可 `--verify` 重算；基线文件支持 `expires` 与 `justification`，过期旧账自动重新报警——竞品没有账本概念。

**技术栈（✅ 成熟依赖，全部为 git 自带能力）**：

- `git merge-tree --write-tree --merge-base=<base> <p1> <p2>`（≥2.38）：机械合并复算，干净时 exit 0 + tree OID，冲突时 exit 1 + 带冲突标记的 tree。
- `git log --merges --remerge-diff -p`（≥2.36）：只看"人改的那部分"；忠实 merge 的 payload 为空。
- `git patch-id --stable` + `git diff-tree -p -U0`：补丁等价判定。
- `git rev-list --cherry-pick --right-only`、`git cherry -v`：跨分支提交对齐。
- `git apply --check / --reverse --check`（临时 worktree）：补丁是否已存在于目标分支的兜底三态。
- `git log --find-object=<blob> --all`：内容是否以其他形式复活/重放。

## 二、任务要求

首期 **5 个模块**，扩展项另列。每模块写清 **输入 / 输出 / 确定性纪律 / 验收**。所有模块共享 `data/README.md` §四的数值口径（三类 hunk 定义、`blob_fidelity`、`patch_parity`、finding ID 构造、基线过期语义），不得在代码或文案中另立第二套口径。

### 模块① `fidelity` — Merge 保真度扫描

- **输入**：仓库路径 + 提交范围（默认 `--all`，或 `<since>..<until>`）。
- **输出**：每个 merge 一条记录：`merge_oid`、`parents`、`merge_base`、`recorded_tree`、`mechanical_tree`（干净/冲突）、`blob_fidelity`、三类 hunk 列表（SMUGGLED / DROPPED / RESOLUTION）、以及 `SKIPPED(reason=...)` 记录。
- **引擎**：
  - 枚举：`git rev-list --merges --reverse --topo-order <range>`。
  - 主路径（单进程批量）：`git log --merges --remerge-diff -p --no-renames --format='%H%x00%P'`，一次进程拿全量 merge payload。
  - 交叉校验：对 payload 非空的 merge 再调 `merge-tree --write-tree --merge-base=<base> <p1> <p2>` 复算机械树，逐 path 比较 blob OID。
  - hunk 分类：`recorded_tree - mechanical_tree` 中**无 CONFLICT 标记**的 hunk = SMUGGLED；`mechanical_tree - recorded_tree` 中**未在后续提交被重新引入**的 hunk = DROPPED；带 CONFLICT 标记的 hunk = RESOLUTION（默认不报，`--show-resolution` 才输出）。
  - `blob_fidelity(merge) = |{path : recorded_oid == mechanical_oid}| / |{path}|`。
  - octopus merge（父提交 >2）与自定义 merge driver（`.gitattributes`）命中的路径：输出 `SKIPPED(reason=octopus|custom_driver)`，**不静默漏报、不影响退出码**。
- **确定性纪律**：不读工作区、不读 index；只用对象库；`--no-renames` 固定；同一仓库同一范围两次运行输出逐字节一致；`SKIPPED` 必须出现在输出里而不是只写日志。
- **验收**：10 个合成 fixture 各注入 1 个已知缺陷（夹带 4 / 静默吞掉 3 / 冲突解决正确 2 / octopus 1），输出与 `data/fixtures/fidelity/*/expect.json` golden 逐字节一致；连跑两次一致；octopus fixture 必须产出 `SKIPPED(reason=octopus)` 且退出码 0。

### 模块② `parity` — 跨分支补丁对齐

- **输入**：两个分支/引用（A=源，B=目标）+ 仓库路径。
- **输出**：`B\A` 中每个提交的三态判定 `PRESENT / MISSING / MODIFIED`，附 `U0_patchid`、等价源提交（若有）、判定依据（`patch-id` 或 `apply-check`）。
- **引擎**：
  - 候选集：`git rev-list --cherry-pick --right-only A...B`；`git cherry -v A B` 作为交叉核对。
  - 等价判定：`git diff-tree -p -U0 <p> <c> | git patch-id --stable`。**必须用 `-U0`**：默认 3 行上下文会让"同一 hunk 出现在第 2 行 vs 第 5 行"的 patch-id 不同（已本地实测）；空白差异（`b b` / `b    b` / `b<TAB>b` / 行尾空格）在 `-U0` 下同 id。
  - 兜底三态：`git worktree add --detach <tmp> <B>` 后在临时 worktree 上 `git apply --check` 与 `git apply --reverse --check`。缺失 → `fwd=0, rev=1`；已应用 → `rev=0, fwd=1`；两者皆非 → `MODIFIED`（部分应用/上下文冲突）。
  - `patch_parity(A,B) = |{c in B\A : U0_patchid(c) in U0_patchid(A)}| / |B\A|`。
  - 临时 worktree 必须 `git worktree remove` 并在异常路径也清理；**不改动任何分支引用**。
- **确定性纪律**：patch-id 计算串行、顺序固定（按 `(commit_time, oid)`）；worktree 路径使用确定性前缀 + 进程内随机后缀，报告里不落绝对路径；同一输入两次运行三态一致。
- **验收**：`release`/`main` 双向合成 fixture——同一修复换上下文（第 2 行 vs 第 5 行）、已应用、部分应用、纯空白差异、真缺失——分类全对；临时 worktree 在成功/异常两条路径下均被清理（`git worktree list` 无残留）。

### 模块③ `ledger` — Revert / 复活账本

- **输入**：仓库路径 + 范围。
- **输出**：每条 revert 一条账目：被回滚 commit、revert commit、`REVERTED_NO_SUCCESSOR` / `REVERTED_THEN_REDONE` 状态、复活证据（重放 commit 或 `--find-object` 命中的提交）。
- **引擎**：
  - 枚举：`git log --grep='^This reverts commit' --format='%H%x00%B'`，从正文提取被回滚 OID。
  - 校验：revert 的 `U0_patchid` 必须等于被回滚 commit 的 diff 取反后的 `U0_patchid`；不等则记 `REVERT_UNVERIFIED(reason=patchid_mismatch)`（不猜测意图）。
  - 重放：`git log --find-object=<blob> --all` 找内容复活；若复活提交的 `U0_patchid` 与原始一致，记 `REVERTED_THEN_REDONE`，否则 `REVERTED_NO_SUCCESSOR`。
  - 只读：不调用 `git revert`，不写 reflog。
- **确定性纪律**：账目按 `(被回滚 commit_time, revert oid)` 排序；同一 revert 只入账一次；`REVERT_UNVERIFIED` 与"没有 successor"是两个不同结论，不得合并。
- **验收**：三种状态（无 successor / 已重做 / patch-id 不匹配）各一个合成 fixture，识别正确且 `--verify` 重算一致。

### 模块④ `report` — 确定性报告 + 可复现摘要

- **输入**：前三个模块的原始结果。
- **输出**：单个规范 JSON（`--format=json`）或 Markdown 摘要（`--format=md`，仅渲染视图，不参与 digest）；每条 finding 的 `id = sha1(commit_oid ‖ path ‖ old_range ‖ new_range ‖ kind)`（拼接用固定分隔符，写入 `data/README.md` §四）。`findings` 汇总三源：`fidelity` 的 hunk、`parity` 的 `PARITY_MISSING`/`PARITY_MODIFIED`、`ledger` 的 `REVERTED_*`；`fidelity` 与 `ledger` **恒计入**，`parity` 需两个显式引用，未给时该节为 `null` 且 `notes` 写 `parity_not_requested`（**不伪造空结果**）。
- **报告头**（写死，参与 digest）：`tool_version`、`git_version`、`object_format`（sha1/sha256）、`gitattributes_oid`（`.gitattributes` 的 blob OID，无则 `null`）、`config_overrides`（生效的 `-c` 覆盖项）、`range`（范围）、`as_of`、`findings_digest_algorithm`（固定 `"sha256"`）。
- **`--verify`**：读回报告文件，用同一份对象库重新推导全部 finding 与 digest，断言与文件字节相等；不等则以退出码 1 报告首个差异（JSON path + 期望/实际）。**定位顺序是"先内容、后 digest"**（先查 digest 会把"哪一处被改了"盖掉）；坏 JSON / 缺 `digest` 字段 = 坏报告 → 退出码 2。
- **确定性纪律**：规范 JSON 按 `(commit_time, commit_oid, path, old_range)` 排序；不写扫描时刻、不写绝对路径、不写主机名、不写用户名/locale/Python 版本；键序固定；换时区（`TZ`）与 `core.quotepath` 设置不改变 digest。
- **验收**：两台机器（不同时区、不同 `core.quotepath`）对同一 fixture 生成同一 digest；`--verify` 退出码 0；手工改一个字节后 `--verify` 退出码非 0 且定位到**被改字段**。

### 模块⑤ `gate` — CI 门禁 + 带过期时间的基线

- **输入**：扫描范围 + `audit-baseline.toml` + `--fail-on=<kind>`。
- **输出**：退出码 + 只含"新增"的报告；基线内旧账单独计数。
- **引擎**：
  - `fidelity scan --since=<tag>`：只扫增量范围。门禁**全量收集 `SMUGGLED` + `DROPPED`**，`--fail-on` 只过滤**新增**是否参与失败（否则另一类已登记的旧账会因"没扫到"被误报成 `stale`）。
  - 基线条目：`id`、`expires`（日期）、`justification`（非空字符串）。命中基线且未过期的 finding 不计入失败；**过期条目自动重新报警**（`expired` 标记，参与退出码）。
  - 基线里指向不存在的 finding（已修复/已删除）标 `stale`，只提示不失败。
  - **受限 TOML 子集**（3.8 无 `tomllib`）：只支持 `[[finding]]` + 单行基本字符串 + 注释；数组 / 嵌套表 / 多行字符串 / 内联表 / 非字符串值 / 未知键 → `toml_unsupported`（退出码 2，**明示行号**）；空基线 → 语法错误。基线先解析再扫描（坏基线**零副作用**）。
  - 退出码：0 = 无新增且无过期；1 = 有新增或过期；2 = 用法/基线语法错误；3 = 环境不满足（git 版本低于门槛）。
- **确定性纪律**：基线解析为纯数据，不做模糊匹配（ID 精确相等）；`expires` 按报告内 `as_of` 日期比较（`as_of <= expires` 含边界当天），不读系统时钟；同一输入两次运行退出码一致。
- **验收**：新增 1 个夹带 → 退出码 1 且只报新增；基线内旧账 → 0；把 `expires` 改到过去 → 1 且标记 `expired`；基线语法错误 → 2。

## 三、提交材料

1. **可安装 CLI 入口**：`pyproject.toml` 的 `[project.scripts]` 定义 `mergefidelity = "mergefidelity.cli:main"`，`pip install -e .` 后可直接运行。
2. **五个子命令的实现**：`src/mergefidelity/{fidelity,parity,ledger,report,gate}.py` + 共享的 `gitobj.py`（只读对象访问）、`canonical.py`（规范 JSON 与 digest）。

4. **基准**：`tools/bench_fidelity.py`（真实仓库全量扫描耗时与单进程/逐进程对比）、`tools/bench_parity.py`、`tools/bench_gate.py`，输出 `bench/*.json`。
5. **测试**：`tests/` 覆盖三类 hunk 分类、patch-id 等价、三态判定、revert 账本、`--verify` 篡改检测、退出码语义。

## 六、边界与非目标

- **不做密钥扫描**：gitleaks / trufflehog 已占，且与本题的"树保真度"无关。
- **不做贡献统计 / bus factor**：hercules / gitinspector 已占。
- **不做仓库体积与大文件审计**：git-sizer 已占。
- **不做分支清理**：deadbranch / git-tidy 已占。
- **不做历史改写**：全程只读 `.git`，不写对象、不改引用、不跑 `filter-branch`/`rebase`；临时 worktree 用完即删。
- **不做"AI 判断代码意图"**：所有结论都由 git 对象与 patch-id 复算得出；不调用模型，不做语义相似度猜测。
- **隐私红线**：纯本地、零网络；报告不写绝对路径、主机名、用户名；不读取 `.env` 等非版本化文件。
- **品牌隔离**：本题是 git 对象层审计，文档与代码中不提名本系列其他工具或项目。
- **首期范围限定**：octopus merge 与自定义 merge driver 统一输出 `SKIPPED(reason=...)`，**显式记录、不静默漏报、不影响退出码**；扩展项（octopus 近似分析、多仓库聚合）不进首期判定路径。
- **结论纪律**：`blob_fidelity` 与 finding 是"机械合并 vs 实际记录"的差异证据，不等于"这段代码错了"；报告必须同时给出机械树与记录树的可复算入口，由人判断业务影响。
